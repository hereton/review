Top Findings

1. Mixed Soft-Delete Strategies Across 12 Tables

7 tables use status TEXT (ACTIVE/INACTIVE), 5 tables use is_active BOOLEAN. No deleted_at timestamp anywhere. Cross-table "active" filtering requires different query patterns depending on the table — split-brain risk for lifecycle management.

2. 13 fmt.Sprintf Dynamic Query Builders

Dynamic WHERE clauses built via fmt.Sprintf across 10 repository files. While all are safe (no user input in format strings), the pattern is harder to audit than a query builder and prone to copy-paste errors in parameter numbering.

3. No Query-Level Context Timeouts

All repository queries rely on parent context deadline with no explicit context.WithTimeout. A long-running query in one handler can starve the connection pool (25 max conns) and cascade to all endpoints.

Quick Wins

1. Add context.WithTimeout Wrapper

Create a middleware in infrastructure/database/ that wraps all queries with a 5s timeout. Effort: ~2h. Impact: prevents pool starvation.

2. Replace 2 SELECT * with Column Lists

assignment_repository.go:403 and ou_master_repository.go:38. Use existing column constants already defined in the same files. Effort: ~15min.

3. Add Index on identity_sources Lookup Columns

identity_sources has 0 custom indexes (only PK). Add composite index on (source_type, connection_status). Effort: ~15min.

C 4.6 Soft Delete & Lifecycle

12 tables with soft-delete: 7 use status TEXT, 5 use is_active BOOLEAN

11 auto-update triggers via fn_set_updated_at()

Anti-patterns (2)
High Mixed soft-delete strategies across 12 tables

Two patterns coexist: status TEXT CHECK IN ('ACTIVE','INACTIVE') (7 tables: applications, roles, permissions, users, org_rules, ou_app_mappings, pc_admins) vs is_active BOOLEAN (5 tables: ou_master, user_role_assignments, pc_roles, user_attributes, attribute_catalog). No deleted_at timestamp on any table.

-- Pattern 1: status TEXT (7 tables)
WHERE status = 'ACTIVE'

-- Pattern 2: is_active BOOLEAN (5 tables)
WHERE is_active = true

-- Cross-table query: must remember which pattern each table uses

Problem: Split-brain risk — "is this record active?" requires different predicates per table. Easy to forget which pattern a table uses.

Solution: Standardize: keep status for user-facing entities, is_active for internal flags. Document the convention in a schema comment.

Medium No deleted_at timestamp for restore audit

Soft-deleted records (status=INACTIVE or is_active=false) have no timestamp recording when they were deactivated. Cannot answer "when was this deactivated?" from the database.

Problem: No restore-point traceability.

Solution: Add deactivated_at TIMESTAMPTZ to key tables, set via trigger or application code.

Healthy Patterns (3)

✓ Consistent audit columns — 14/27 tables have created_at, created_by, updated_at, updated_by

✓ Auto-update triggers — 11 tables use fn_set_updated_at() trigger for updated_at

✓ No hard DELETE in application code — All lifecycle changes via status/is_active updates
