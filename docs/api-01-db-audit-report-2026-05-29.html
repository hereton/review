Critical Findings

Hardcoded database credentials in source code

Problem: internal/config/config.go contains a hardcoded fallback DSN with username admin, password StrongPassword123!, and internal IP 172.31.42.28:8111.

Solution: Remove the hardcoded default. Fail fast when DATABASE_URL is not set. Use secret management (Vault, AWS Secrets Manager) in production.

Mixed soft-delete strategies across tables

Problem: Four different soft-delete patterns coexist: deleted_at (GORM, roles), is_active (users, applications), status varchar (roles, permissions, assignments), and archived_at (ABAC entities). Each requires different query logic.

Solution: Standardize on one pattern per entity category. Prefer deleted_at for GORM-managed tables and status for state-machine entities. Document the convention.

15+ dropped tables across migration history

Problem: Aggressive schema churn through 4 phases (RBAC → ABAC → EAV → unified). 15+ tables were created and later dropped, indicating significant architectural pivots. While each has proper down migrations, the accumulated debris makes the migration history harder to reason about.

Solution: Consider squashing migrations into a clean baseline once the schema stabilizes. Document the phase evolution clearly.

Quick Wins

Remove hardcoded DB credentials from config.go

One-line fix: change fallback to empty string. Add startup validation. ~15 minutes.

Add CHECK constraints to status columns

Several status VARCHAR columns lack CHECK constraints. Add CHECK (status IN ('active','inactive')) to roles, permissions, ou_role_mappings. ~1 hour.

Document soft-delete convention per table

Create a single-page doc mapping each table to its soft-delete mechanism. ~30 minutes.

B+ Schema & Table Design

Files: migrations/000001_create_applications.up.sql through migrations/000082_seed_super_admin_nuttawut.up.sql

16 live tables, ~160 columns total. Schema evolved through 4 phases: RBAC (001-018), menu system (027-030), ABAC (038-061), unified (062-082).

Anti-patterns (3)
High Mixed identity column strategies

Problem: Most tables use BIGSERIAL for PKs but created_by columns vary: BIGINT (ou_role_mappings), VARCHAR(200) (user_access_assignments, presets), BIGINT (audit_logs.actor_id). Same semantic role, different types.

Solution: Standardize created_by as BIGINT REFERENCES users(id) for actor tracking, or VARCHAR for external/system actor names. Pick one pattern per use case.

Medium Missing description/text on several tables

Problem: role_permissions, preset_permissions, group_attributes are pure junction tables with no metadata columns (no created_at, no created_by). Makes auditing changes to these tables impossible.

Solution: Add created_at TIMESTAMPTZ NOT NULL DEFAULT NOW() at minimum to junction tables that represent user actions.

Medium user_ou_exclusions uses manual soft-delete

Problem: user_ou_exclusions has a deleted_at column but isn't a GORM model (no gorm.DeletedAt in Go struct). Soft-delete is manual — SELECT queries must remember to filter WHERE deleted_at IS NULL.

Solution: Either adopt GORM soft-delete in the Go model or use a status column pattern consistent with other tables.

Healthy Patterns (8)

BIGSERIAL for all primary keys — consistent auto-increment identity

TIMESTAMPTZ used universally for all temporal columns — no timezone-naive timestamps

VARCHAR with length constraints on all string columns — no unbounded TEXT except for description/payload fields

UNIQUE constraints on business identifiers (applications.code, users.oid, roles per app+code)

Clean normalization — no god tables (max ~15 columns), proper junction tables for M:N relationships

JSONB for audit payload — flexible schema-free payload in audit_logs without sacrificing query capability

Custom ENUM types — 4 PostgreSQL ENUMs for constrained value sets (sync_status, sync_trigger, sync_type, permission_type)

Phase-aware migration naming — sequential numbering (000001-000082) with descriptive names reflecting evolution phases

101 foreign key references across all migrations. Comprehensive FK coverage on live tables.

Anti-patterns (2)
Medium Missing CHECK constraints on status columns

Problem: ou_role_mappings.status, user_ou_exclusions.status are VARCHAR(20) without CHECK constraints. Any string value is accepted at the DB level.

-- ou_role_mappings: status VARCHAR(20) with no CHECK
-- roles.status: VARCHAR(20) with no CHECK
-- Should be:
ALTER TABLE ou_role_mappings
  ADD CONSTRAINT chk_ou_status CHECK (status IN ('active','inactive'));
Medium Nullable columns that should be NOT NULL

Problem: user_access_assignments.created_by VARCHAR(200) is nullable — who granted the access should always be recorded. permissions.permission_group is nullable but used for grouping logic.

Solution: Make created_by NOT NULL with a default or require it at application level.

ON DELETE SET NULL for optional relationships (audit_logs.application_id)

ON DELETE RESTRICT on critical FKs (user_access_assignments.role_id, role_permissions.permission_id)

Composite UNIQUE constraints on junction tables (role_permissions.role_id+permission_id, user_access_assignments compound unique)

FK coverage — every logical relationship in the current schema is backed by a foreign key

CHECK constraint on roles.role_type — CHECK (role_type IN ('rbac', 'abac')) during Phase 3 transition

UNIQUE (application_id, code) on roles — prevents duplicate role codes within an app scope

B- Soft Delete & Lifecycle

4 different soft-delete strategies coexist across the schema.

Strategy Tables Mechanism
deleted_at roles, user_ou_exclusions GORM soft-delete / manual
is_active users, applications Boolean toggle
status roles, permissions, ou_role_mappings, user_ou_exclusions VARCHAR state machine
archived_at (historical ABAC tables, now dropped) Timestamp archival
Anti-patterns (3)
High Dual soft-delete on roles: deleted_at AND status

Problem: roles has both deleted_at (GORM soft-delete) and status ('active'/'inactive'). Two independent "is this alive?" signals create split-brain risk: a role can be soft-deleted (deleted_at set) but still 'active', or vice versa.

Solution: Choose one mechanism. If using GORM soft-delete, drop the status column or make it purely informational (not for lifecycle). If using status, remove deleted_at and handle GORM's hooks.

Medium Hard delete on user_role_assignments (now dropped)

Problem: The old user_role_assignments table had no soft-delete mechanism — records were hard-deleted. The new user_access_assignments also lacks soft-delete. Historical access changes are only captured via audit_logs.

Solution: Rely on audit_logs as the historical record, which is the current pattern. This is acceptable if audit_logs are comprehensive and immutable.

Medium user_ou_exclusions: manual soft-delete not via GORM

Problem: The deleted_at column exists in the DB but the Go model doesn't use gorm.DeletedAt. Application code must manually filter WHERE deleted_at IS NULL. If any query path forgets, "deleted" exclusions leak into access calculations.

Solution: Add DeletedAt gorm.DeletedAt to the Go model so GORM auto-filters, or switch to a status-based approach.

Healthy Patterns (3)

Comprehensive audit_logs — dedicated table with actor, action, entity type+id, JSONB payload, and timestamp

Partial index for active records — idx_users_is_active WHERE is_active = TRUE efficiently filters active users

Deactivation tracking on users — deactivated_at + deactivation_reason columns record why a user was deactivated

D+ Security & Access
Anti-patterns (2)
Critical Hardcoded database credentials in config.go

Problem: internal/config/config.go:32 contains a hardcoded fallback DSN: postgresql://admin:StrongPassword123!@172.31.42.28:8111/mydb?sslmode=disable. This is committed to source control, visible in git history, and could be used in production if DATABASE_URL is not set.

DatabaseURL: envOrDefault("DATABASE_URL",
  "postgresql://admin:StrongPassword123!@172.31.42.28:8111/mydb?sslmode=disable"),

Solution: Remove hardcoded default. Use os.Getenv("DATABASE_URL") with startup validation that fails if empty. Rotate the exposed credentials immediately.

High sslmode=disable in default connection string

Problem: The default DSN uses sslmode=disable. If this fallback is ever used, database connections would be unencrypted.

Solution: Default to sslmode=require or let the environment variable control SSL mode explicitly.
