Presentation Layer

Anti-patterns

  • handler/activity_handler.go — Calls repository interfaces directly, bypassing Application layer entirely. Uses domain.AuditLogRepository and domain.ApplicationRepository.
  • handler/audit_log_handler.go — Calls domain.AuditLogRepository directly. Contains business validation logic for category filtering (lines 46-51).
  • handler/ou_master_handler.go — Calls domain.OUMasterRepository directly. Contains complex conditional cascade logic (lines 47-96). Defines local response DTO struct ouCascadeResponse.
  • handler/health_handler.go — Imports sqlx.DB directly. Presentation→Infrastructure layer violation.
  • middleware/pc_permission.go — Performs database query via repository (GetPermissionCodesByEmail) in middleware.
  • middleware/login_hook.go — Calls usecase (LoginHookUsecase.Execute) from middleware, mixing business orchestration with HTTP middleware.
  • All handlers — Scattered error mapping: each handler duplicates the same handleXxxError switch pattern mapping domain errors to HTTP status codes.
  • handler/ou_master_handler.go:28-33 — Response DTO defined in handler instead of domain.

Healthy Patterns

  • Thin handlers: Most handlers follow parse → call usecase → map response → return.
  • Consistent envelope: All responses use domain.Success() and domain.Error().
  • Interface dependency: Handlers depend on domain usecase interfaces, not concrete implementations.
  • Input validation at edge: Syntax/format checks in handler via domain.ValidateEnglishSpace().
  • Grouped routes: Related endpoints nested under same handler struct/file.

Top Recommendation

Start with Candidate 2 Close the Handler-to-Repository Shortcut

Fixing the four skip-layer calls restores the architecture's core invariant: handlers must delegate to usecases, never call repositories directly. This is the highest-impact change because it unblocks all other improvements — centralized error mapping (Candidate 1) can't work cleanly while some handlers bypass the usecase layer, and extracting business logic from repositories (Candidates 4-5) is harder when handlers depend on raw repository behavior.

Recommended Order

  1. Step 1 Candidate 2 — Create thin usecases for ActivityHandler, AuditLogHandler, OUMasterHandler. Move HealthHandler to infrastructure. Restores layer boundaries.
  2. Step 2 Candidate 1 — Centralize error mapping. Now that all handlers go through usecases, the error mapper has a single seam. Reduces handler boilerplate by ~15 lines each.
  3. Step 3 Candidate 3 — Extract infrastructure types from domain. Move JSONB and pq types to infrastructure adapters. Purifies domain layer.
  4. Step 4 Candidate 5 — Extract hardcoded business constants. Define status/threshold constants in domain. Single source of truth for business rules.
  5. Step 5 Candidate 4 — Split oversized repositories. Leverage candidates 2-3 first to ensure clean interfaces.
  6. Step 6 Candidate 6 — Split wide service interfaces. Speculative — only if team feels pain from wide mocks.
Layers affected: Presentation → Application → Domain → Infrastructure. Start with Presentation (restore delegation), then move inward.
