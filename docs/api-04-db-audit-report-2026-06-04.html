4. Layer-by-Layer Audit

4.1 Schema & Table Design — B+

18 active tables across 56 up migrations. Schema evolved through clear phases: RBAC foundation → Azure AD integration → OU-based role mapping → ABAC master data → delegation system. Clean normalization — no god tables (largest is user_abac_assignments at ~20 columns). BIGSERIAL PKs, TIMESTAMPTZ throughout, proper use of JSONB for preset data and audit payloads. UUID PK for sync_logs is a good choice for distributed tracking.

Anti-patterns
High Dual-status columns on roles and applications

Roles have both status VARCHAR(20) and deleted_at TIMESTAMPTZ (GORM soft-delete). Applications have both is_active BOOLEAN (original) and status VARCHAR(20) (added later). Two sources of truth for "is this active?" creates split-brain risk.

-- roles table has BOTH:
status VARCHAR(20) NOT NULL DEFAULT 'active'  -- application-level
deleted_at TIMESTAMPTZ                         -- GORM soft-delete

-- applications table has BOTH:
is_active BOOLEAN NOT NULL DEFAULT TRUE  -- original
status VARCHAR(20) NOT NULL DEFAULT 'active'  -- added in 000026
Medium Seed data mixed with schema migrations

7 migration files contain INSERT/seed data (test users, applications, roles, ABAC master data). Seed data should be separate from schema migrations for cleaner rollbacks and environment portability.

000025_seed_applications.up.sql (20 lines)
000033_seed_test_users.up.sql (68 lines)
000043_seed_pc_roles.up.sql (12 lines)
000053_seed_webproold_app.up.sql (4 lines)
000054_seed_abac_master_webproold.up.sql (79 lines)
000055_seed_abac_delegations_webproold.up.sql (127 lines)
Low Mystery column f1 on user_role_assignments

Column f1 VARCHAR(100) on user_role_assignments has no clear purpose in the codebase. Appears to be a leftover from a previous schema iteration.

Healthy Patterns
  • BIGSERIAL primary keys on all tables — proper 64-bit auto-increment
  • UUID PK for sync_logs — appropriate for distributed sync tracking
  • TIMESTAMPTZ used consistently (no plain timestamp anywhere in codebase)
  • JSONB for flexible payload storage (audit_logs, permission_ids)
  • Clean separation of RBAC entities: roles, permissions, role_permissions junction
  • No god tables — largest table (user_abac_assignments) has ~20 columns
  • Nullable OU fields on users correctly allow wildcard matching
4.2 Constraints & Integrity — B

25 FK constraints with appropriate ON DELETE strategies: CASCADE for dependent data (assignments → users), SET NULL for audit-safe references (audit_logs → applications). Composite FKs on ABAC tables for (bu_id, division_id). CHECK constraints present on ABAC status columns and date validation.

Anti-patterns
High Missing CHECK constraints on early status columns

Early tables (roles, applications, permissions) use VARCHAR(20) status with no CHECK constraint. Only ABAC-era tables have proper CHECK constraints. The DB will accept any string for early tables.

-- No CHECK constraint on roles.status:
status VARCHAR(20) NOT NULL DEFAULT 'active'

-- ABAC tables have proper CHECK:
status VARCHAR(20) NOT NULL DEFAULT 'active'
    CHECK (status IN ('pending', 'active', 'inactive', 'archived'))
Medium created_by FK removed from ou_role_mappings

Originally created_by BIGINT NOT NULL REFERENCES users(id), migration 000034 converted to VARCHAR(100) with no FK. The referential integrity to users table is lost.

Medium Nullable columns that should be NOT NULL

created_by and updated_by on several tables are nullable. For audit integrity, the actor should always be recorded.

Healthy Patterns
  • 25 FK constraints — every logical relationship enforced at DB level
  • Composite FKs for ABAC tables: FOREIGN KEY (bu_id, division_id) REFERENCES abac_divisions(bu_id, id)
  • Thoughtful ON DELETE: CASCADE for assignments, SET NULL for audit logs
  • CHECK constraints on ABAC status columns and date validation (chk_uabac_date_order, chk_abac_deleg_dates)
  • Partial UNIQUE indexes for soft-delete compatibility
4.3 Indexing Strategy — A-

Strong indexing strategy. 45+ indexes including partial/conditional indexes, composite indexes matching query patterns, and unique indexes for data integrity. FK columns are almost all indexed. Index-to-table ratio > 2.5.

Anti-patterns
Low ou_role_mappings.created_by lacks FK index

The created_by column was originally a FK to users(id) but now is VARCHAR(100). No index exists for lookups by creator.

Healthy Patterns
  • Partial indexes for filtered queries: WHERE is_active = TRUE, WHERE deleted_at IS NULL
  • Composite indexes matching query patterns: (application_id, user_id), (application_id, type)
  • Conditional unique indexes for active records: WHERE status = 'active'
  • Index-to-table ratio > 2.5 (45 indexes for 18 tables) — well-indexed
  • External ID indexes with WHERE external_id IS NOT NULL — avoids indexing NULLs
  • Date-range indexes for effective/expires: WHERE status IN ('pending', 'active')
4.4 Migration Management — C+

56 sequential migrations with 100% down-migration coverage. Sequential numbering (000001-000056) using golang-migrate. Migrations embedded via Go's iofs. Main issues: 6 dropped tables (migration debris), 7 seed files mixed with schema, and an irreversible ENUM extension.

Anti-patterns
Critical 6 tables created then dropped — migration debris

Tables token_sessions, ad_groups, user_ad_groups, menus, role_menu_mappings, permission_center_migrations, permission_center_seeds were all created and later dropped. This reflects evolutionary design but adds significant noise to the migration history.

-- 000022_drop_token_sessions.up.sql:  DROP TABLE token_sessions
-- 000023_drop_ad_groups.up.sql:        DROP TABLE user_ad_groups, ad_groups
-- 000029_drop_role_menu_mappings.up.sql: DROP TABLE role_menu_mappings
-- 000030_drop_menus.up.sql:            DROP TABLE menus
-- 000036_drop_permission_center_migrations_table.up.sql
-- 000037_drop_permission_center_seeds_table.up.sql
High 7 seed/data migrations mixed with schema

INSERT and UPDATE statements appear in migration files alongside schema changes. Makes rollbacks risky and environments non-portable.

Medium Irreversible ENUM extension (migration 000050)

Adding values to sync_type ENUM is irreversible in PostgreSQL. The down migration cannot remove the added values. This is a PostgreSQL limitation but should be noted for future ENUM changes.

-- 000050_extend_sync_type_enum_for_abac.up.sql
ALTER TYPE sync_type ADD VALUE 'abac_master';
ALTER TYPE sync_type ADD VALUE 'abac_assignment';
ALTER TYPE sync_type ADD VALUE 'abac_delegation';
-- Cannot be reversed: ENUM values cannot be removed in PostgreSQL
Medium Complex data migrations mixed with schema

Migration 000034 (26 lines) converts updated_by from "user:" format to actual user names across 4 tables. Migration 000056 (26 lines) normalizes JSONB to child table. Both mix data transformation with schema concerns.

Healthy Patterns
  • 100% down migration coverage — every up has a matching down
  • Sequential numbering (000001-000056) — clear ordering
  • Migrations embedded in Go binary via iofs — no external file dependency
  • IF EXISTS / IF NOT EXISTS used for safe re-application
  • Descriptive file names: create_*, add_*, drop_*, rename_*, fix_*
4.5 Query Patterns — B+

20 repository files with strong query hygiene. Zero SELECT * usage, zero fmt.Sprintf SQL injection risk, 7 transaction boundaries, batch-first approach with IN clause lookups. Pagination capped at 20 rows (default) / 200 rows (max). Good use of GORM's WithContext for timeout control.

Anti-patterns
High Loop-based INSERT in SetScopeApps

manage_user_repository.go lines 500-509 uses a for loop with individual INSERT statements instead of a single bulk INSERT. This is slower and creates more round-trips.

for _, appID := range appIDs {
    if err := tx.Exec(
        `INSERT INTO pc_admin_app_assignments...`,
    ).Error; err != nil {
        return err
    }
}
// Should use: INSERT INTO ... VALUES (...), (...), (...)
Low Offset-based pagination only

All pagination uses LIMIT/OFFSET. For large datasets, cursor-based pagination would be more efficient. Currently mitigated by 200-row hard cap.

Healthy Patterns
  • Zero SELECT * — all queries use explicit column selection
  • Zero fmt.Sprintf SQL construction — all parameterized via GORM ? placeholders
  • 7+ transaction boundaries for multi-table writes with proper error handling
  • Anti-N+1: batch queries with Where("user_id IN ?", userIDs)
  • Consistent pagination: 20-row default, 200-row max
  • GORM's WithContext for timeout/cancellation support
  • Complex COALESCE-based wildcard matching for OU field alignment
  • UNION queries for effective role resolution (OU mapping + manual assignment)
4.6 Soft Delete & Lifecycle — C-

Four different soft-delete strategies coexist in the codebase: is_active boolean (users, abac_bus/divisions/roles, delegation_pair_configs), status VARCHAR column (roles, applications, permissions, user_abac_assignments, abac_delegations), deleted_at TIMESTAMPTZ (roles only), and archived_at TIMESTAMPTZ (ABAC tables). The ABAC-era pattern (status + archived_at + CHECK) is the strongest but inconsistently applied.

Anti-patterns
Critical 4 incompatible soft-delete strategies

No single query can retrieve "all active records" consistently. Each table group needs a different WHERE clause:

-- Pattern 1: is_active boolean — users, abac_bus, abac_divisions, abac_roles
WHERE is_active = TRUE

-- Pattern 2: status column — applications, permissions, ou_role_mappings
WHERE status = 'active'

-- Pattern 3: status + archived_at — user_abac_assignments, abac_delegations
WHERE status = 'active' AND archived_at IS NULL

-- Pattern 4: deleted_at (GORM) — roles only
WHERE deleted_at IS NULL
High Dual-status on roles: status + deleted_at

roles has both status VARCHAR(20) AND deleted_at TIMESTAMPTZ (GORM DeletedAt). A role could be "inactive" by status but not soft-deleted, or soft-deleted but status='active'. Which takes precedence?

High Dual-status on applications: is_active + status

Applications originally had is_active BOOLEAN, then status VARCHAR(20) was added in migration 000026 with a backfill. Both coexist. The index idx_applications_status implies status is the primary, but is_active still exists.

4.7 Naming Conventions — C+
Anti-patterns
Medium created_by / updated_by type mismatch across tables

Early tables use VARCHAR(100), ABAC-era tables use VARCHAR(200). The ou_role_mappings originally had BIGINT REFERENCES users(id) (FK to users) which was converted to VARCHAR. Same concept, three different types.

-- ou_role_mappings (originally):
created_by BIGINT NOT NULL REFERENCES users(id)  -- FK, then converted to VARCHAR(100)

-- user_role_assignments:
created_by VARCHAR(100)  -- name

-- user_abac_assignments / abac_delegations:
created_by VARCHAR(200)  -- name, wider
updated_by VARCHAR(200) NOT NULL DEFAULT 'sync-job'
Medium Column naming scar: group_col vs expected group

permissions.group_col avoids the SQL reserved word group, but the naming is inconsistent with the convention used elsewhere. Consider permission_group instead.

Low Mystery column name f1

f1 VARCHAR(100) on user_role_assignments — non-descriptive name, unclear purpose.

Healthy Patterns
  • Consistent snake_case for all table and column names
  • Plural table names (users, roles, applications) — consistent convention
  • Standard index naming: idx_{table}_{columns}, uq_{table}_{purpose}
  • Consistent TIMESTAMPTZ (no plain timestamp anywhere)
  • BIGSERIAL id on all tables as PK
  • Consistent {entity}_id pattern for FK columns
4.8 Security & Access — D+
Anti-patterns
Critical Hardcoded production credentials in config.go

Default DATABASE_URL includes production credentials: username postgres, password -Vz*_Vf=}#1sRTD6. If DATABASE_URL env var is not set, the app connects to production with known credentials.

// internal/config/config.go
User: url.UserPassword("postgres", "-Vz*_Vf=}#1sRTD6")
High Default fallback connects to production

The config uses a fallback pattern — if env var is empty, it defaults to a hardcoded production connection. This means a misconfigured deployment silently connects to the wrong database.

Medium No RLS (Row-Level Security) policies

No PostgreSQL RLS policies defined. Security is entirely application-level. For a permission center, database-level access control would add defense-in-depth.

Healthy Patterns
  • Production connection uses sslmode=require — encrypted in transit
  • Environment variable loading pattern exists for DATABASE_URL
  • All SQL queries parameterized — zero SQL injection risk
  • Dockerfile runs as non-root user app
  • Multi-stage Docker build — no build tools in production image
4.9 Performance & Scaling — B
Anti-patterns
Medium No visible connection pool tuning

Connection pool parameters (MaxOpenConns, MaxIdleConns, ConnMaxLifetime) not configured — relies on Go sql.DB defaults which may not be optimal for production load.

Low Offset-based pagination only

All pagination uses LIMIT/OFFSET. For large datasets, cursor-based pagination would be more efficient. Currently mitigated by 200-row hard cap.

Healthy Patterns
  • GORM WithContext for query timeout/cancellation
  • 200-row pagination hard cap prevents unbounded queries
  • Batch operations using IN clauses for bulk lookups
  • Extensive partial indexes reduce index size and improve query speed
  • COMPOSITE FK indexes on ABAC tables for (bu_id, division_id) lookups
