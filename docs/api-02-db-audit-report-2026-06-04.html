4. Layer-by-Layer Audit

4.1 Schema & Table Design — B+

16 active tables across 98 up migrations. Schema evolved through multiple phases (RBAC → ABAC merge, Groups experiment, Attribute-based assignments). Clean normalization — no god tables (largest is users at ~15 columns). BIGSERIAL PKs, TIMESTAMPTZ throughout, proper use of JSONB for audit payloads.

Anti-patterns
High Dual-status columns on roles

Both status VARCHAR(20) and deleted_at TIMESTAMPTZ (GORM soft-delete) exist on the roles table. Two sources of truth for "is this role active?" creates split-brain risk.

-- roles table has BOTH:
status VARCHAR(20) NOT NULL DEFAULT 'active'  -- application-level
deleted_at TIMESTAMPTZ                         -- GORM soft-delete
Medium Seed data mixed with schema migrations

18 migration files contain INSERT/seed data (test users, applications, roles). Seed data should be separate from schema migrations for cleaner rollbacks and environment portability.

-- 000025_seed_applications.up.sql
-- 000033_seed_test_users.up.sql
-- 000043_seed_pc_roles.up.sql
-- 000082_seed_super_admin_nuttawut.up.sql
Low Mystery column f1 on user_access_assignments

Column f1 VARCHAR(100) on user_access_assignments has no clear purpose in the codebase. Appears to be a leftover from a previous schema iteration.

Healthy Patterns
  • BIGSERIAL primary keys on all tables — proper 64-bit auto-increment
  • TIMESTAMPTZ used consistently (no plain timestamp anywhere in codebase)
  • JSONB for flexible payload storage (audit_logs, background_jobs)
  • Clean separation of RBAC entities: roles, permissions, role_permissions junction
  • No god tables — largest table (users) has ~15 columns, well under 25-column threshold
  • Nullable OU fields on users correctly allow wildcard matching
4.2 Constraints & Integrity — A-

Comprehensive FK coverage. 30+ foreign keys with appropriate ON DELETE strategies: CASCADE for dependent data (assignments → users), RESTRICT for protect-in-use data (assignments → roles), SET NULL for optional references (audit_logs → applications).

Anti-patterns
High Missing CHECK constraints on status columns

Most status columns are VARCHAR(20) with no CHECK constraint. The DB will accept any string. Only ou_role_mappings and some conditional UNIQUE indexes enforce values.

-- No CHECK constraint on roles.status:
status VARCHAR(20) NOT NULL DEFAULT 'active'
-- Should be:
status VARCHAR(20) NOT NULL DEFAULT 'active'
    CHECK (status IN ('active', 'inactive'))
Medium Nullable columns that should be NOT NULL

created_by on several tables is nullable. For audit integrity, the creator should always be recorded.

Healthy Patterns
  • 30+ FK constraints — every logical relationship is enforced at DB level
  • Thoughtful ON DELETE strategies: CASCADE for user-scoped data, RESTRICT for shared entities, SET NULL for audit-safe references
  • Partial UNIQUE indexes for soft-delete compatibility: WHERE deleted_at IS NULL
  • Composite FK support used correctly (e.g., abac_divisions composite key)
4.3 Indexing Strategy — A

Excellent indexing strategy. 40+ indexes including partial/conditional indexes, composite indexes matching query patterns, and unique indexes for data integrity. FK columns are properly indexed.

Healthy Patterns
  • Partial indexes for filtered queries: WHERE is_active = TRUE, WHERE deleted_at IS NULL
  • Composite indexes matching ACL query patterns: (application_id, user_id)
  • Conditional unique indexes for soft-delete compatibility: WHERE deleted_at IS NULL
  • Covering indexes for common filter+sort patterns
  • Index-to-table ratio > 2.5 (40 indexes for 16 tables) — well-indexed
4.4 Migration Management — B-

98 sequential migrations with 100% down-migration coverage. Sequential numbering (000001-000098) using golang-migrate. Migrations embedded via Go's iofs. The main issue is seed data and complex data migrations mixed into schema files.

Anti-patterns
High 18 seed/data migrations mixed with schema

INSERT and UPDATE statements appear in migration files alongside schema changes. This makes rollbacks risky and environments non-portable.

  • IF EXISTS / IF NOT EXISTS used for safe re-application
  • Dirty state recovery in migration runner
4.5 Query Patterns — A

25 repository files (~6,900 lines) with excellent query hygiene. Zero SELECT * usage, zero fmt.Sprintf SQL injection risk, 15 transaction boundaries, batch-first approach with Preload and batch ID lookups. Pagination capped at 200 rows. Transactional outbox pattern for background jobs.

Healthy Patterns
  • Zero SELECT * — all queries use explicit column lists
  • Zero fmt.Sprintf SQL construction — all parameterized
  • 15+ transaction boundaries for multi-table writes
  • Anti-N+1: batch FindByIDs, Preload, UNION queries for ACL resolution
  • Pagination with 200-row hard cap + total count
  • FOR UPDATE SKIP LOCKED for concurrent job processing
  • RETURNING + ON CONFLICT for upserts
  • Transactional outbox pattern — Enqueue accepts parent tx
4.6 Soft Delete & Lifecycle — C+

Three different soft-delete strategies coexist in the codebase: deleted_at (GORM soft-delete on roles), status column (applications, permissions, ou_role_mappings), and is_active boolean (users). The latest pattern (migration 000098) uses deleted_at + removed_by + removal_reason on user_access_assignments — this is the best pattern but inconsistently applied.

Anti-patterns
High Mixed soft-delete strategies across tables

Three incompatible patterns make it hard to query "all active records" consistently:

-- Pattern 1: deleted_at (GORM) — roles
WHERE deleted_at IS NULL

-- Pattern 2: status column — applications, permissions
WHERE status = 'active'

-- Pattern 3: is_active boolean — users
WHERE is_active = TRUE

-- Pattern 4: deleted_at + removed_by + reason — user_access_assignments
WHERE deleted_at IS NULL  (with audit trail)
High Dual-status on roles table

roles has both status VARCHAR(20) AND deleted_at TIMESTAMPTZ (GORM DeletedAt). A role could be "inactive" by status but not soft-deleted, or soft-deleted but status='active'. Which takes precedence?

Medium UserAccessAssignment uses plain *time.Time, not gorm.DeletedAt

Deliberate choice documented in model comment — raw SQL ACL queries wouldn't get GORM's automatic filtering. Correct engineering decision but adds inconsistency.
