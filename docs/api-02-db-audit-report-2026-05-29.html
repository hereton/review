Anti-patterns (2)
High Roles table has dual-status: status + deleted_at

The roles table has both a status TEXT column and a deleted_at TIMESTAMPTZ column (added in migration 008). This creates split-brain: a role can be "inactive" via status but not soft-deleted, or soft-deleted but status still "active". GORM's soft-delete hooks and application status checks can conflict.

-- 000003: original roles table
CREATE TABLE roles (..., status TEXT DEFAULT 'active');
-- 000008: adds deleted_at alongside existing status
ALTER TABLE roles ADD COLUMN deleted_at TIMESTAMPTZ;
-- Now two mechanisms control lifecycle

Problem: Dual-status creates ambiguity — which column is the source of truth for "is this role active"?

Solution: Pick one: use GORM deleted_at for soft-delete and drop status, or use status and remove deleted_at. Recommend keeping deleted_at since GORM supports it natively.

Medium Inconsistent PK naming: id vs table_singular_id

All tables use id BIGSERIAL PRIMARY KEY (generic), not the {table_singular}_id pattern. While consistent within this project, it differs from api-03 which uses application_id, role_id, etc. Not wrong, but can cause ambiguity in JOIN-heavy queries with multiple id columns.

Solution: Low priority — always use aliases in JOINs. Consider adopting {singular}_id pattern for new tables.

✓ Well-normalized schema — Clear separation: applications, users, roles, permissions as core entities; junction tables for M:N relationships

✓ TIMESTAMPTZ everywhere — All temporal columns use timestamptz, no plain timestamp without timezone

✓ Proper evolution through phases — Schema evolved through 4 phases (basic RBAC → ABAC → EAV → unified), each with proper migration files

✓ JSONB for flexible data — attribute_values, old_values/new_values in audit_logs properly use JSONB

Anti-patterns (3)
High Data migrations mixed with schema migrations

Seed data files (000025, 000033, 000043, 000053-000055, 000082) are numbered alongside schema DDL. Data migrations like 000058 (merge ABAC roles) and 000085 (email deduplication) combine ALTER TABLE with INSERT/UPDATE in the same file.

-- 000058_merge_abac_roles_into_roles.up.sql
-- Schema change mixed with data transformation:
ALTER TABLE roles ADD COLUMN role_type TEXT;
UPDATE roles SET role_type = 'rbac';
INSERT INTO roles (...) SELECT ... FROM abac_roles;
ALTER TABLE abac_roles ADD COLUMN rbac_role_id BIGINT;
UPDATE abac_roles SET rbac_role_id = ...;

Problem: If data transformation fails partway, schema change is already committed. Harder to test and retry independently.

Solution: Split complex migrations: schema change in one file, data transformation in a separate numbered migration.

Medium 178 destructive DROP operations across history

20+ tables were created then dropped across 4 phases (token_sessions, ad_groups, menus, abac_bus, etc.). While each has a matching down migration, the volume increases cognitive load and migration replay time.

Solution: Consider squashing migration history after Phase 4 is stable. Create a single baseline migration from the current schema state.

Medium Application-specific seed data in migration sequence

Migration 000054 and 000055 seed "webproold" application data. Migration 000082 seeds a specific super admin user (nuttawut). These are environment-specific and should not be in the migration sequence that runs on every environment.

Solution: Move environment-specific seed data to a separate seed runner outside the migration sequence.

✓ 100% down migration coverage — All 85 up migrations have matching down migrations

✓ Sequential numbering — 000001 through 000085, easy to read and order

✓ Descriptive names — Each migration name describes the action (create_applications, merge_abac_roles_into_roles, add_users_email_unique)

✓ IF NOT EXISTS guards — DDL uses IF NOT EXISTS / IF EXISTS for idempotent replay safety

C+ 4.6 Soft Delete & Lifecycle
Anti-patterns (3)
Critical 3 different soft-delete strategies across tables

// Pattern A: status TEXT — roles, permissions, ou_role_mappings, attributes, groups, delegations

status TEXT NOT NULL DEFAULT 'active'
    CHECK (status IN ('active', 'inactive', 'pending', 'archived')),

// Pattern B: is_active BOOLEAN — applications, users

is_active BOOLEAN NOT NULL DEFAULT TRUE,

// Pattern C: deleted_at TIMESTAMPTZ (GORM) — roles, user_ou_exclusions

deleted_at TIMESTAMPTZ,  -- GORM soft-delete
-- GORM scopes: db.Unscoped() to include deleted

Problem: Split-brain — same conceptual operation ("deactivate") uses 3 mechanisms, each requiring different query patterns and filter logic. The roles table uses BOTH Pattern A and Pattern C simultaneously.

Solution: Standardize on one pattern. Recommend GORM's deleted_at for all mutable tables (already partially in use). Add gorm.DeletedAt to all models.

High Roles: dual-status (status + deleted_at on same table)

The roles table has both status TEXT and deleted_at TIMESTAMPTZ. GORM's soft-delete operates on deleted_at, while application logic checks status. A role could be "active" via status but soft-deleted via deleted_at IS NOT NULL, or vice versa.

Solution: Remove status from roles and rely entirely on GORM's deleted_at for soft-delete. Use is_self or a role_type column for classification instead.

Medium is_active vs status semantics unclear

applications and users use is_active BOOLEAN while roles, permissions, ou_role_mappings use status TEXT. The choice between boolean and text status isn't documented and doesn't follow an obvious pattern (e.g., not correlated with table complexity).

Solution: Standardize: use status TEXT for entities with multiple lifecycle states (pending/active/inactive/archived), deleted_at for soft-delete, drop is_active where redundant.

Healthy Patterns (2)

✓ GORM soft-delete support — Models using gorm.DeletedAt get automatic WHERE deleted_at IS NULL scoping

✓ Comprehensive audit columns — created_at, updated_at, created_by, updated_by on most mutable tables

Critical Issues (2)
Critical Hardcoded production database credentials in source code 
// internal/config/config.go:39
DatabaseURL: envOrDefault("DATABASE_URL",
    "postgresql://admin:StrongPassword123!@172.31.42.28:8111/mydb?sslmode=disable"),

// cmd/fix_migration/main.go:12

Problem: Production database credentials (host, username, password) committed to git. The default fallback means the app works even without environment variables — silently connecting to production with hardcoded credentials.

Solution: Remove default value from config.go. Fail fast if DATABASE_URL is not set. Delete or read from env in fix_migration tool. Rotate the exposed password immediately.

High Debug logging of DATABASE_URL in server startup

cmd/server/main.go:164 logs the DATABASE_URL value, which includes the password. Log output may be captured in log aggregation systems, exposing credentials in log storage.

Solution: Mask the password in log output, or remove the DATABASE_URL from startup logging entirely.

B 4.9 Performance & Scaling
Anti-patterns (2)
Medium No explicit connection pool configuration

GORM uses default connection pool settings (unlimited max open connections, 2 idle connections). No SetMaxOpenConns, SetMaxIdleConns, SetConnMaxLifetime, or SetConnMaxIdleTime configured.

Problem: Under load, unlimited connections can exhaust PostgreSQL's connection limit (default 100). No idle timeout means stale connections may accumulate.

Solution: Configure pool: SetMaxOpenConns(25), SetMaxIdleConns(10), SetConnMaxLifetime(30*time.Minute).

Medium LIMIT/OFFSET pagination only — no cursor-based pagination

All list endpoints use OFFSET (page-1)*pageSize LIMIT pageSize. OFFSET scans and discards rows — O(n) cost on deep pages.

Solution: For high-volume tables (users, audit_logs), add keyset/cursor pagination option (WHERE id > last_seen_id ORDER BY id LIMIT N).

Healthy Patterns (3)

✓ Max page size enforced — 200 item cap prevents unbounded result sets

✓ Comprehensive indexing — 132 indexes with partial indexes for common filter patterns

✓ Proper pagination implementation — Consistent LIMIT/OFFSET with reasonable defaults (20-50)
