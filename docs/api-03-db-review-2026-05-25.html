  WHERE email = rp.created_by LIMIT 1),

Audit Log Partitions Have Hard End Date

Worth Exploring

migrations/000001_init_schema.up.sql:530-547 (18 monthly partitions)

migrations/000001_init_schema.up.sql:527 (DEFAULT partition)

// Last partition — hard stop at 2027-07

CREATE TABLE audit_logs_y2027m06 PARTITION OF audit_logs
  FOR VALUES FROM ('2027-06-01') TO ('2027-07-01');

// After 2027-07-01 — everything lands here (unpartitioned)

CREATE TABLE audit_logs_default PARTITION OF audit_logs DEFAULT;

↑ No auto-create, no pg_partman — partitioning silently degrades

Problem: Lifecycle seam — partitions end at 2027-06 with no auto-create mechanism. After that, all rows funnel into the unpartitioned default partition, silently degrading query performance.

Solution: Add pg_partman or a scheduled job to auto-create monthly partitions 3-6 months ahead.

Permissions Dual Status (DB + Computed Bool)

Worth Exploring

internal/domain/permission.go:15 (IsActive bool `db:"-"`)

internal/domain/permission.go:16 (Status string `db:"status"`)

internal/domain/permission.go:24-27 (SyncIsActive method)

internal/domain/permission.go:30-34 (StatusFromActive conversion)

// permission.go — two representations of same fact

IsActive bool   `db:"-" json:"is_active"`     // API layer
Status   string `db:"status" json:"-"`         // DB layer

// Conversion — must be called after every DB scan

func (p *Permission) SyncIsActive() {
    p.IsActive = p.Status == "ACTIVE"
}

// Reverse conversion — API bool → DB string

func StatusFromActive(isActive bool) string {
    if isActive { return "ACTIVE" }
    return "INACTIVE"
}

↑ If someone forgets SyncIsActive(), API returns wrong data

Problem: Split-brain — two representations of the same fact across API and DB layers. If SyncIsActive() is missed after a scan, the API returns stale/incorrect active state.

Solution: Keep status TEXT in DB, compute IsActive only at the handler/response boundary, never store it on the struct.

⚠ SyncIsActive() required after every Select/Get

⚠ Easy to forget → wrong API response

After — status only, compute at edge

Permission struct

Status string `db:"status"` — single source

Handler layer

response.IsActive = perm.Status == "ACTIVE"

✓ Computed at boundary, no sync needed

✓ No SyncIsActive() to forget

✓ Single field on struct

No sync method Single field Less bug surface

Hard Delete on Junction Tables vs Soft Delete Elsewhere

Speculative

internal/repository/role_permission_repository.go:59 (DELETE FROM role_permissions)

migrations/000001_init_schema.up.sql:200-207 (role_permissions — no status column)

migrations/000001_init_schema.up.sql:253-260 (org_rule_roles — no status column)

// role_permission_repository.go — hard DELETE

DELETE FROM role_permissions WHERE role_id = $1

// Migration — junction tables have no status/is_active

CREATE TABLE role_permissions (
  role_id       BIGINT NOT NULL REFERENCES roles ON DELETE CASCADE,
  permission_id BIGINT NOT NULL REFERENCES permissions ON DELETE CASCADE,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  created_by    TEXT NOT NULL,
  PRIMARY KEY (role_id, permission_id)
);

↑ No soft-delete column — deleted rows are gone permanently

Problem: Lifecycle seam — parent entities use soft delete but junction rows are permanently destroyed. Accidental bulk un-assign cannot be undone without restoring from backup.

Solution: Either soft-delete junction rows (add status column) or document as acceptable since junction recreation is idempotent via BulkSet.
