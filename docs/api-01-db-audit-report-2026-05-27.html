Top Findings

1. Hardcoded Production Credentials in Source Code

config.go:32 has postgresql://admin:StrongPassword123!@172.31.42.28:8111/mydb?sslmode=disable as default DSN. cmd/fix_migration/main.go:12 has the same DSN hardcoded. .gitlab-ci.yml:36 contains SSH password P@55w0rd@2025. All committed to version control.

2. No Connection Pooling Configured

gorm.Open(postgres.Open(cfg.DatabaseURL), &gorm.Config{}) in cmd/server/main.go:104 with no subsequent SetMaxOpenConns, SetMaxIdleConns, or SetConnMaxLifetime. Under load, unbounded connections can exhaust the database.

3. Dual Soft-Delete on Roles Table (Split-Brain Risk)

roles has both status VARCHAR(20) DEFAULT 'active' and deleted_at TIMESTAMPTZ. GORM's SoftDelete sets deleted_at but does not update status, making status='active' AND deleted_at IS NOT NULL possible. Queries must check both columns.

Quick Wins

1. Remove Hardcoded Credentials from Defaults

Replace default DSN in config.go with empty string + validation. Move SSH password to GitLab CI/CD variables. Effort: ~30min.

2. Add GORM Connection Pooling

After gorm.Open: sqlDB.SetMaxOpenConns(25), sqlDB.SetMaxIdleConns(10), sqlDB.SetConnMaxLifetime(5 * time.Minute). Effort: ~15min.

3. Add CHECK Constraints to Status Columns

4 tables have status VARCHAR(20) without CHECK — any string accepted. Add CHECK (status IN ('active','inactive','archived')) on roles, ou_role_mappings, groups, attributes. Effort: ~1h.

C+ 4.1 Schema & Table Design

migrations/ — 82 up + 82 down files, ~2,260 lines up total

Active tables: applications, users, roles, permissions, role_permissions, ou_role_mappings,

audit_logs, sync_logs, role_permission_presets, preset_permissions, pc_admin_app_assignments,

user_ou_exclusions, attributes, groups, group_attributes, user_access_assignments

Anti-patterns (3)
High 15 dropped/deprecated tables — extreme schema churn

Tables created then fully dropped in later migrations: token_sessions, ad_groups, user_ad_groups, menus, role_menu_mappings, abac_bus, abac_divisions, abac_roles, user_abac_assignments, user_abac_attributes, abac_attribute_keys, abac_attribute_values, abac_delegations, delegation_pair_configs, user_role_assignments. Complete ABAC feature was implemented and removed.

Problem: Schema history is cluttered with dead code. New developers must trace which tables are active.

Solution: Consider a consolidation migration that creates the current schema from scratch in a clean state, leaving the old migrations as historical reference only.

Medium BIGSERIAL instead of GENERATED ALWAYS AS IDENTITY

All tables use BIGSERIAL PRIMARY KEY instead of PostgreSQL 10+ BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY. BIGSERIAL creates a sequence with weaker ownership semantics.

Problem: BIGSERIAL sequences can be accidentally dropped or altered independently of the column.

Solution: For new tables, use IDENTITY columns. Existing tables are fine — migration risk outweighs benefit.

Medium ENUM types cannot be removed (PostgreSQL limitation)

4 custom ENUM types: permission_type, sync_status, sync_trigger, sync_type. PostgreSQL does not support removing ENUM values (ALTER TYPE ... ADD VALUE is irreversible).

Solution: Accept current ENUMs. For new status fields, prefer VARCHAR + CHECK constraint for flexibility.

Healthy Patterns (5)

✓ IF NOT EXISTS guards — Most DDL uses IF NOT EXISTS / IF EXISTS for idempotent replay safety

✓ TIMESTAMPTZ everywhere — All temporal columns consistently use timestamptz

✓ JSONB for flexible data — audit_logs.payload uses JSONB for structured audit trail

✓ Proper normalization — Junction tables (role_permissions, group_attributes, preset_permissions) follow many-to-many pattern correctly

✓ Permission tree hierarchy — Self-referencing parent_id on permissions with SET NULL on delete

B- 4.2 Constraints & Integrity

migrations/ — 57 FKs, ~10 CHECK constraints, 10+ UNIQUE constraints

Anti-patterns (2)
High Missing CHECK constraints on status columns (4 tables)

roles.status, ou_role_mappings.status, groups.status, attributes.status are all VARCHAR(20) NOT NULL DEFAULT 'active' without CHECK. Any string value is accepted.

-- Current: any string accepted
status VARCHAR(20) NOT NULL DEFAULT 'active'

-- Should be:
status VARCHAR(20) NOT NULL DEFAULT 'active'
  CHECK (status IN ('active', 'inactive', 'archived'))

Problem: Application-level validation is the only guard. A bug or direct SQL session could insert invalid status values.

Solution: Add CHECK constraints via migration. Data validation should happen at the database level as the source of truth.

High Dual status columns on roles (status + deleted_at)

The roles table has both status VARCHAR(20) and deleted_at TIMESTAMPTZ. GORM's DeletedAt type automatically scopes queries with WHERE deleted_at IS NULL, but the status column is not synchronized.

Problem: A soft-deleted role via GORM still has status='active'. Queries filtering only on status will include deleted roles.

Solution: Choose one mechanism per table. Either remove deleted_at and use status only, or remove status and use GORM soft-delete exclusively.

Healthy Patterns (4)

✓ Good FK coverage on active tables — All logical relationships have FK constraints

✓ CASCADE on junction tables — role_permissions, preset_permissions use CASCADE for automatic cleanup

✓ CHECK constraints where applied — attributes.data_type IN ('string','number','date','enum'), user_ou_exclusions.reason has length check

✓ UNIQUE composite constraints — Proper multi-column unique constraints on junction tables (role_id+permission_id, group_id+attribute_id)

B- 4.4 Migration Management

migrations/ — 82 up + 82 down files (164 total)

Naming: 6-digit sequential (000001_description.up.sql)

Tool: golang-migrate v4.19.1 with embedded FS (iofs)

Anti-patterns (2)
High 15 destructive DROP TABLE migrations in up files

Extensive table drops across migrations, mostly from ABAC feature rollback (migrations 000058-000073). While each has a corresponding down migration, data loss is permanent after running up.

-- 000061_drop_abac_bu_division.up.sql
DROP TABLE IF EXISTS abac_bus;
DROP TABLE IF EXISTS abac_divisions;

-- 000073_drop_abac_delegation_tables.up.sql
DROP TABLE IF EXISTS abac_delegations;
DROP TABLE IF EXISTS delegation_pair_configs;

Problem: Destructive migrations in up files mean any environment that runs migrations forward permanently loses data.

Solution: For future feature deprecation, consider archiving data to a backup table before dropping.

Medium Data migrations mixed with schema migrations

5+ files combine ALTER TABLE with UPDATE/INSERT backfills. Examples: migration 000026 (is_active to status conversion), 000034 (user ID to name conversion), 000058 (ABAC roles merge).

Problem: Data backfills in DDL transactions can cause long locks on large tables.

Solution: Separate schema changes from data transformations. Run data migrations independently with monitoring.

Healthy Patterns (4)

✓ 100% down migration coverage — All 82 up migrations have matching down migrations

✓ Sequential numbering — 6-digit sequential (000001 through 000082), easy to read and order

✓ Descriptive names — Each migration describes its action (e.g., add_status_deleted_at_to_roles, merge_abac_roles_into_roles)

✓ Embedded FS for migrations — Uses iofs for single-binary deployment, no external file dependency

C- 4.6 Soft Delete & Lifecycle
Anti-patterns (3)
High 4 different soft-delete strategies across tables

// Pattern A: status VARCHAR — ou_role_mappings, groups, attributes, roles

status VARCHAR(20) NOT NULL DEFAULT 'active'

No CHECK constraint — any string accepted

// Pattern B: deleted_at TIMESTAMPTZ — roles, user_ou_exclusions

deleted_at TIMESTAMPTZ,
deleted_by VARCHAR(200)
-- GORM DeletedAt auto-scopes WHERE deleted_at IS NULL

// Pattern C: is_active BOOLEAN — applications, users

is_active BOOLEAN NOT NULL DEFAULT TRUE

// Pattern D: hard DELETE — role_permissions, preset_permissions, user_access_assignments

DELETE FROM role_permissions WHERE role_id = ?

Problem: Same operation ("deactivate") requires 4 different query patterns. Developers must know which pattern each table uses.

Solution: Standardize on status VARCHAR + CHECK for mutable tables. Junction tables keep hard DELETE (document as intentional).

High Dual status + deleted_at on roles (split-brain)

Roles table has status VARCHAR(20) AND deleted_at TIMESTAMPTZ. GORM soft-delete sets deleted_at but does not update status. Possible state: status='active' AND deleted_at IS NOT NULL.

Problem: Queries filtering on only one column will return inconsistent results.

Solution: Remove deleted_at from roles and use status exclusively, or remove status and use GORM soft-delete.

Medium Raw SQL must manually handle deleted_at IS NULL

GORM's DeletedAt auto-scopes ORM queries, but raw SQL in repositories must manually add AND deleted_at IS NULL. Missed checks lead to soft-deleted roles appearing in results.

// acl_repository.go — must manually check:
JOIN roles ro ON ro.id = m.role_id
    AND ro.deleted_at IS NULL    -- manual soft-delete check
    AND ro.status = 'active'
Healthy Patterns (2)

✓ user_ou_exclusions preserves history — Soft-deleted exclusions are retained with deleted_by for audit trail

✓ audit_logs with JSONB payload — Every significant operation logs old/new values for full traceability

C+ 4.9 Performance & Scaling
Anti-patterns (2)
Critical No connection pooling configured 
// cmd/server/main.go:104
db, err = gorm.Open(postgres.Open(cfg.DatabaseURL), &gorm.Config{})
// No SetMaxOpenConns, SetMaxIdleConns, or SetConnMaxLifetime

Problem: Under load, unlimited connections can exhaust database resources. Idle connections are never recycled, leading to stale connections.

Solution: Add after gorm.Open: sqlDB, _ := db.DB(); sqlDB.SetMaxOpenConns(25); sqlDB.SetMaxIdleConns(10); sqlDB.SetConnMaxLifetime(5 * time.Minute)

Medium OFFSET/LIMIT pagination only — no cursor-based pagination

All list endpoints use OFFSET/LIMIT. For current scale this is acceptable, but will degrade as data grows.

Solution: Consider keyset pagination for high-volume queries: WHERE id > last_seen_id ORDER BY id LIMIT N.

✓ Batch Create operations — CreateBatch in ou_repository, BulkCreate in access_assignment_repository

✓ Proper indexing for common queries — Composite indexes match actual query patterns

✓ Enforced max page size — Pagination capped at 200 rows to prevent unbounded queries
