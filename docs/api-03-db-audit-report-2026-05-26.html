Top Findings

1. Mixed Soft-Delete Strategies (3 patterns)

7 tables use status TEXT, 3 use is_active BOOLEAN, 4 junction tables use hard DELETE. Split-brain risk: same conceptual operation requires different query patterns.

2. N+1 Queries in Assignment Creation

assignment_usecase.go loops user×role for duplicate checks (N×M queries) and fetches display data per-row after batch insert (N queries). For 50 users × 5 roles = 250 duplicate checks + 250 fetches.

3. user_role_assignments Near God-Table (17 columns)

Widest table in schema — mixes core assignment data with metadata (f1_ref_no, note), lifecycle (effective/expire dates), and provenance (org_rule_id, assignment_type). Consider splitting metadata.

Quick Wins

Replace N×M FindDuplicate calls with a single SELECT ... WHERE (user_id, role_id, app_id) IN (...) query. Effort: ~2h.

2. Replace SELECT * in FindAutoAssignment

Two SELECT * usages in assignment_repository.go:387 and ou_master_repository.go:17. Replace with explicit column list. Effort: ~15min.

3. Standardize Soft-Delete on status TEXT

Add migration to convert is_active BOOLEAN to status TEXT CHECK IN ('ACTIVE','INACTIVE') on 3 tables. Effort: ~4h with migration + code update.

B- 4.6 Soft Delete & Lifecycle
Anti-patterns (2)
High 3 different soft-delete strategies

// Pattern A: status TEXT — 7 tables

status TEXT NOT NULL DEFAULT 'ACTIVE'
   CHECK (status IN ('ACTIVE', 'INACTIVE')),

applications, roles, permissions, org_rules, ou_app_mappings, pc_admins, users

// Pattern B: is_active BOOLEAN — 3 tables

is_active BOOLEAN NOT NULL DEFAULT true,

user_role_assignments, ou_master, pc_roles

// Pattern C: hard DELETE — 4 junction tables

role_permissions, org_rule_roles, pc_role_permissions, pc_admin_app_scope

Problem: Split-brain — same conceptual operation ("deactivate") uses 3 mechanisms, each requiring different query patterns and filter logic.

Solution: Standardize on status TEXT CHECK IN ('ACTIVE','INACTIVE') across all mutable tables. Junction tables keep hard DELETE (document as intentional for cleanup).

Low No deleted_at timestamp tracking

Soft-deleted rows have no record of when they were deactivated. The updated_at timestamp serves as a proxy but is not semantically equivalent.

Solution: Low priority — updated_at + audit_logs provide sufficient traceability for this system.
